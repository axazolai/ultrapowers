# Ultrapowers

Библиотека скиллов для Claude Code: разработка через тесты, систематическая отладка,
планирование, ревью кода и связывающие их практики совместной работы. Скиллы подгружаются по
необходимости и объявляют себя — видно, какой из них сейчас ведёт.

[🇬🇧 English](README.md) | 🇷🇺 Русский

## Происхождение и лицензия

Ultrapowers — это **форк [obra/superpowers](https://github.com/obra/superpowers)** Джесси
Винсента (Jesse Vincent), используемый и распространяемый по лицензии **MIT**. Копирайт в
`LICENSE` — авторский, апстримовый, он остаётся неизменным в каждой сборке.

Форк существует, чтобы делать одно дело хорошо, а не семь сносно: он рассчитан только на Claude
Code. Это сужение, а не улучшение — если вы работаете в Codex, Cursor, Gemini, Kimi, opencode или
Pi, ставьте апстрим: он поддерживает их все и его ведут те, кто эти скиллы написал.

## Установка

```
/plugin marketplace add axazolai/ultrapowers
/plugin install ultrapowers@ultrapowers
```

Затем перезапустите Claude Code: набор включённых плагинов резолвится только при старте,
hot-reload'а нет.

## Чем отличается от апстрима

Собрано из **апстрима 6.4.1**; версия плагина выводится как `<версия апстрима>-up.<ревизия>`,
поэтому эта сборка — `6.4.1-up.1`. Ревизия растёт с изменениями форка на одной базе апстрима и
сбрасывается в 1 на новой базе. Всё, что не перечислено ниже, — работа апстрима, перенесённая
без изменений.

### Охват и идентичность

- **Только Claude Code.** Манифесты, адаптеры и справки других харнессов не переносятся, как и
  собственные тесты апстрима, его релизные инструменты и история разработки. Из 231 файла
  апстрима поставляются 72: манифест, хук `SessionStart`, скиллы и `LICENSE`. В
  `using-ultrapowers` остаётся одна справка по платформе — для Claude Code, с опциональной
  удешевлённой оркестровкой subagent-driven development, — а сервер brainstorming читает версию
  только из `.claude-plugin/plugin.json`.
- **Переименовано целиком**, чтобы оба плагина можно было поставить рядом и вызов скилла был
  однозначным: `ultrapowers:brainstorming` разрешается сюда, а скиллы апстрима остаются в своём
  пространстве имён.
- **Манифест и бренд-ссылка указывают на форк** — homepage, repository, автор, — а в описании
  назван апстрим, так что `/plugin` показывает происхождение без чтения README.

### Режим тестирования: tdd или test-after

У каждого проекта есть режим тестирования, он задаётся `/ultrapowers-tdd enable|disable`
(хранится в `.claude/ultrapowers.json`; нет файла — test-after):

- **tdd** — разработка через тесты по апстриму: сначала падающий тест, RED → GREEN → REFACTOR,
  TDD-доказательства в отчётах задач, исправления после финального ревью через RED → GREEN.
- **test-after** — сначала код; когда единица работы готова целиком и до её ревью, спека/план
  сверяются с решениями, принятыми по ходу, баги этой единицы из лога чинятся, и пишется по
  одному тесту на заявленное поведение с мутационной проверкой. Планы несут список
  `Acceptance:` вместо кода тестов.

В обоих режимах: баг, не мешающий работе, уходит в `BUGS.md` и чинится перед ревью единицы или
в конце; решение, меняющее поведение, сначала попадает в спеку; строки Review Focus плана
входят в список тестов задачи-владельца; находки ревьюера о поведении, о котором спека молчит,
идут партнёру — он вносит каждую в спеку или отклоняет; каждое падение в прогоне называется в
отчёте поимённо.

### Планирование живёт в дереве, а не в датированных файлах

Апстрим пишет дизайны в `docs/ultrapowers/specs/YYYY-MM-DD-<topic>-design.md`, а планы — в
`docs/ultrapowers/plans/YYYY-MM-DD-<feature>.md`. Здесь оба лежат в одной директории фазы,
названной по тому, что работа решает:

- `bash scripts/phase-dir phase|task|adhoc <slug>` находит и печатает
  `.ultrapowers/phases/NN-<slug>/`, выделяя номер выше максимального существующего и никогда не
  используя его повторно. Повторный вызов с тем же slug возвращает ту же директорию, поэтому
  brainstorming, `writing-plans`, `subagent-driven-development` и `executing-plans` не
  разъезжаются по разным местам для одной фазы.
- Спека фазы — `NN-SPEC.md` в корне директории, план — `NN-PLAN.md`, вспомогательные дизайны —
  в `refs/` рядом. Документ, служащий нескольким фазам, идёт в `.ultrapowers/docs/`.
- Workspace плана назван по директории фазы и записывает владельца; второй план, претендующий
  на него, получает отказ, а не общий каталог.
- Ничего в дереве не создаётся заранее: папка появляется, когда в ней есть что положить.

### Исполнение плана — через субагентов или нативно

- **Тесно связанные задачи идут одному агенту целой цепочкой**, а не по агенту на задачу.
- **Кто пишет какой документ — зафиксировано.** `NN-SPEC.md` и `NN-PLAN.md` остаются в основной
  сессии (это диалоги); `NN-SUMMARY.md` и `NN-VERIFICATION.md` отдаются субагентам через
  `summary-writer-prompt.md` и `verification-prompt.md`, которые возвращают путь и вердикт, а не
  текст документа.
- **Оба исполнителя заканчивают одинаково.** Сначала ledger читается «холодно» — дешёвый
  субагент получает только путь к ledger'у и должен сказать, что это за фаза, что сделано, что
  открыто и что дальше; пробел закрывается раньше всего остального. Затем пишутся summary и
  verification, обновляются файлы состояния, и только потом workspace удаляется — поимённо,
  никогда рекурсивно. Summary — запись, которая его переживает.
- **Статус-файлы сохраняют историю.** `ROADMAP.md` и `NN-STATE.md` переписываются, а не
  дописываются, но законченное помечается закрытым и остаётся записью, оставшаяся работа
  поднимается выше, а сверху — короткое резюме.

### Brainstorming и решенческие записи

- **Факты — твоя забота, решения — забота партнёра.** Вопрос, на который отвечает файловая
  система, история git или установленные версии, выясняется, а не задаётся. Каждый вопрос несёт
  свой рекомендуемый ответ и обоснование, дерево решений проходится в порядке зависимостей.
- **Дрейф стека проверяется один раз, на этапе дизайна** — `node
  ~/.claude/hooks/lib/stack-rules-check.mjs <root>`, сообщается только при `stale`.
- **Две секции дизайна обязательны**: *Testing Decisions* (список приёмки, который подтвердят
  тесты, и швы, на которых поведение будет проверено) и *Out of Scope*.
- **Запись в глоссарий делается в момент уточнения термина**, а не пачкой в конце.
- **ADR пишется, только если решение трудно обратимо, неожиданно без контекста и было настоящим
  компромиссом** — все три условия.

### Проверки плана, которые исполняются

Самопроверка плана апстрима читается свежим взглядом. Здесь пункты 5 и 6 *исполняются*: каждая
команда, которую план велит запустить исполнителю, сначала запускается в том worktree, где он
будет работать, — в режиме test-after только то, что уже существует на момент плана, — и каждый
инвариант из блока Interfaces задачи исполняется на её же примере кода.

### Ревью кода

Перед проверками идёт **структурный пре-пасс**: `fallow` по изменённым файлам, результаты — в
секцию Issues с его же серьёзностью. В GSD-проекте (есть `.planning/`) пропускается; без
бинарника `fallow` в JavaScript-проекте сводится к одной Minor-заметке с командой установки, в
остальных — молча пропускается.

### Диагностика сессии

`diagnosing-ultrapowers` держит свой workspace в scratchpad проекта
(`.claude/.scratchpad/diagnosing/<session-id>/`), не имеет шага с GitHub issues и запускает семь
параллельных аналитиков только с разрешения партнёра.

### Дельты, для полноты

Каждое изменение выше — отдельный нумерованный патч в ветке `patch`, применяемый при сборке:

| дельта | что меняет |
|---|---|
| `001-fallow-graft` | структурный пре-пасс в ревью кода |
| `002-drop-platform-adaptation` | в `using-ultrapowers` остаётся только справка Claude Code |
| `003-plugin-version-source` | сервер brainstorming читает только манифест Claude Code |
| `004-plugin-manifest` | идентичность форка в `plugin.json`, апстрим назван в описании |
| `005-brand-link` | бренд-ссылка в UI brainstorming ведёт на форк |
| `006-grilling-fact-lookup` | дисциплина интервью в brainstorming |
| `007-planning-tree` | директория фазы вместо датированных путей в `docs/`; workspace по имени фазы |
| `008-sdd-summary` | «холодная» перечитка ledger'а и `NN-SUMMARY` до поимённого удаления workspace |
| `009-agent-first` | кто какой документ пишет; статус-файлы с историей; связанные задачи — одному агенту |
| `010-design-records` | проверка дрейфа стека, обязательные секции, глоссарий и ADR |
| `011-planning-rules-are-run` | пункты 5 и 6 проверки плана исполняются, а не перечитываются |
| `014-test-after-coverage` | режим тестирования (tdd / test-after), лог багов, находки вне спеки — партнёру |
| `015-diagnosing-in-project` | диагностика в scratchpad проекта, без GitHub issues, аналитики — по разрешению |

Три файла форк пишет сам, а не патчит апстримовые:
`skills/brainstorming/scripts/phase-dir`,
`skills/subagent-driven-development/summary-writer-prompt.md` и
`skills/subagent-driven-development/verification-prompt.md`.

## Как это собирается

Плагин генерируется и никогда не правится руками. Три ветки:

| ветка | что хранит |
|---|---|
| `original` | нетронутые снимки апстрима — по коммиту на релиз, с тегом `upstream/<версия>` |
| `patch` | карта плагина, преобразование переименования и наши изменения отдельными нумерованными дельтами |
| `main` | сгенерированный результат: `original` + `patch`, готовый к установке |

Пересборка, не воспроизводящая `main` побайтово, считается дефектом, и сборка об этом сообщает.
Процедура обновления — в README репозитория.
